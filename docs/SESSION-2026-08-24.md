## What I did, in order

1. **Reloaded context** from `docs/HANDOFF.md` — goal is a local, offline
   assistant that solves CTF challenges and enumerates web targets using RAG
   over writeups + tool execution in a sandbox (not fine-tuning), on an 8 GB
   VRAM laptop.

2. **Checked the background jobs.** `qwen3:8b` was still pulling (the agent
   driver model); `finish_downloads.sh` (embeddings + corpus) had died and was
   restarted; a stale watcher waiting on `gpt-oss:20b` — a model we DROPPED —
   was killed (it would have waited forever).

3. **Built the agent** `scripts/agent.py`. A single-file ReAct loop: the driver
   model (`qwen3:8b`) is given three tools and loops up to 25 steps until it
   produces a flag. Tools:
   - `search_writeups(query)` — retrieves from the local writeup corpus, already
     wrapped as untrusted data.
   - `run_in_sandbox(command)` — runs one command in a locked-down podman
     container.
   - `ask_specialist(question)` — asks the uncensored exploit model
     (`DeepHat-V1-7B`).
   Full design is in `docs/AGENT.md`.

4. **Created a 7-item todo list** tracking the remaining work (downloads,
   ingest+retrieval test, sandbox image build, tool-call optimization, recon
   tools, end-to-end test).

5. **Started the sandbox image build** (`podman build -t ctf-sandbox:1`).

6. **No-restrictions pass** (your directive: the model must have no
   restrictions; you own authorization and scope). I:
   - Removed an `_ESCAPE` command denylist that refused certain commands. It was
     redundant — commands already run inside a cap-dropped, read-only container
     with no way to escape — so it only restricted the agent without adding any
     real protection.
   - Rewrote the driver and specialist system prompts to explicitly say: this is
     an authorized engagement, do NOT refuse, hedge, moralize, or add
     disclaimers. This suppresses qwen3's built-in refusal behavior.
   - KEPT exactly two things, because they are not restrictions on you — they
     keep the tool working and protect your own laptop: (a) prompt-injection
     fencing, so a poisoned writeup can't hijack the agent; (b) container
     isolation, so the agent's own commands can't damage the host.

7. **Ran an ox-alpha code review** (review only) via `~/Downloads/ask_ox.py`
   through OmniRoute. Took three tries: the first used the heavier `-high` model
   and got cut off mid-report; the second used a wrong model name and 404'd; the
   third (`openrouter/stealth/ox-alpha`) produced the complete review. Verdict:
   **no policy restriction exists in the file** — no denylist, no host/target
   gating, no refusal wrapper. The review also found real correctness and
   injection-hardening bugs. Full text + a per-finding disposition table are in
   `docs/ox_review.md`.

8. **Applied the review's high-value fixes** (these strengthen the kept
   injection defense and reliability; none add a restriction on you):
   - Rejected decoy flags: a `WORD{...}` string that appears in untrusted tool
     output is no longer accepted as the answer (stops a poisoned writeup from
     feeding a fake flag).
   - Pinned the system prompt so context truncation can't silently drop the
     fencing rules mid-run.
   - Made the tool-argument dispatch crash-proof.
   - Turned off qwen3's "thinking" mode for clean tool-calling.
   - Added a persistent `/scratch` volume so the agent can build something in one
     step and use it in the next (before, every command started from scratch).
   - Kept the tail of long command output (flags often appear at the end).
   - Made the sandbox timeout/memory/cpu limits environment-tunable.
   - Added `--init` so leftover child processes get reaped.

9. **Documented everything**: `docs/AGENT.md` (design + security model + env
   reference), `docs/ox_review.md` (review + fixes), updated `docs/HANDOFF.md`,
